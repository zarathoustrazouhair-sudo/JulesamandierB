  data_type,

SELECT
  conname AS constraint_name,
  contype AS constraint_type,  -- 'p'=primary key, 'u'=unique, 'f'=foreign key, 'c'=check, 'x'=exclusion

FROM pg_constraint
WHERE conrelid = 'public.payments'::regclass;

-- All indexes on a table
SELECT
  indexname,
  indexdef
FROM pg_indexes
WHERE tablename = 'payments'

  kcu.column_name,
  ccu.table_name AS foreign_table_name,
  ccu.column_name AS foreign_column_name,

JOIN information_schema.key_column_usage AS kcu

## 17. RACE CONDITION AND MEMORY LEAK PREVENTION MANDATE

### 17.1 — Payment Validation Race Condition

The payment validation workflow has a known race condition window: between the UI calling `UPDATE payments SET statut='valide'` and the PostgreSQL trigger inserting into `flux_tresorerie`, a concurrent validation of the same payment by a second authenticated user (e.g., two gestionnaire sessions) can result in a duplicate `flux_tresorerie` entry even if the `EXCLUDE` constraint prevents a second `payments` row.

**Jules MUST implement an optimistic lock on payment validation:**

```typescript
// REQUIRED pattern in ValidationButton handler
const { data, error } = await supabase
  .from('payments')
  .update({
    statut: 'valide',
    valide_par: user.id,
    valide_at: new Date().toISOString()
  })
  .eq('id', paymentId)
  .eq('statut', 'en_attente')  // ← OPTIMISTIC LOCK: only succeeds if still en_attente
  .select()
  .single();

if (!data) {
  // Payment was already validated by another user (concurrent modification)
  throw new Error('Ce paiement a déjà été traité par un autre utilisateur.');
}
```

The `.eq('statut', 'en_attente')` clause is the optimistic lock. If the row was already validated concurrently, the UPDATE matches 0 rows, `data` is null, and the UI surfaces the conflict to the user instead of silently succeeding.

### 17.2 — Realtime Subscription Memory Leaks

The `useMatrixData` hook and any other hook using Supabase Realtime channels MUST implement proper cleanup. Failure to call `channel.unsubscribe()` on unmount causes memory leaks, duplicate event handlers, and phantom state updates after navigation.

**Jules MUST implement this exact pattern:**

```typescript
// src/hooks/useMatrixData.ts — REQUIRED cleanup pattern
import { useEffect, useRef, useCallback, useReducer } from 'react';
import { supabase } from '@/lib/supabase/client';
import type { RealtimeChannel } from '@supabase/supabase-js';

export function useMatrixData() {
  const [state, dispatch] = useReducer(matrixReducer, initialState);
  const channelRef = useRef<RealtimeChannel | null>(null);
  const isMountedRef = useRef(true);  // ← prevents state update on unmounted component

  const fetchData = useCallback(async () => {
    const { data, error } = await supabase.rpc('get_matrix_data');
    if (!isMountedRef.current) return;  // ← guard against stale async callback
    if (error) {
      dispatch({ type: 'SET_ERROR', payload: error.message });
    } else {
      dispatch({ type: 'SET_DATA', payload: data });
    }
  }, []);

  useEffect(() => {
    isMountedRef.current = true;
    fetchData();

    // Subscribe to payment changes that invalidate matrix state
    channelRef.current = supabase
      .channel('matrix-payments-changes')
      .on('postgres_changes', {
        event: 'UPDATE',
        schema: 'public',
        table: 'payments',
        filter: 'statut=eq.valide'
      }, () => {
        if (isMountedRef.current) fetchData();
      })
      .subscribe();

    return () => {
      isMountedRef.current = false;  // ← mark unmounted before async cleanup
      if (channelRef.current) {
        supabase.removeChannel(channelRef.current);  // ← explicit channel removal
        channelRef.current = null;
      }
    };
  }, [fetchData]);

  return state;
}
```

**Critic must flag any Realtime subscription that does not follow this pattern as a memory leak defect.**

### 17.3 — Additional Race Conditions Jules Must Guard Against

**Resident deactivation race**: If a syndic deactivates a resident (`actif=false`) while that resident's payment is being validated by a gestionnaire, the FK `payments.resident_id` becomes a stale reference. Guard: validate `residents.actif = true` in the payment form's apartment selector query.

**AG quorum race**: If two syndic sessions record attendance simultaneously, `ag_presences` may receive duplicate rows for the same `(session_id, appartement_id)` pair. Guard: the `UNIQUE CONSTRAINT uq_presence_per_session` at DB level handles this, but the UI must catch the `23505` error and display "Présence déjà enregistrée pour cet appartement."

**Serial ID race**: The PostgreSQL `nextval()` call in `generate_serial_id()` is atomic and non-transactional — it will never produce duplicates even under concurrent trigger firings. This is by design; Jules must NOT attempt to generate serial IDs in application code.
